# LOCAL-next-target-advisor — Spec Grill

Evidence: scratchpad research files plus targeted fetches of `WidgetClosed.java`, `VarPlayerID.java`, `InterfaceID.java` from runelite master.

## Findings

1. **BLOCKER — B2 "fail the build on any enum constant without an entry" fails on day one.** Diffing `Quest.java` (211 constants) against `Module:Questreq/data` top-level keys (182, one of which is the `Name_of_quest` template stub) gives 40 enum constants with no exact key: the 10 Recipe for Disaster subquests (wiki `Recipe for Disaster/Freeing Pirate Pete` vs enum `Recipe for Disaster - Pirate Pete`, `Freeing the Goblin generals` vs `Wartface & Bentnoze`, `Defeating the Culinaromancer` vs `Culinaromancer`) and 30 miniquests/new quests absent from the module (Barcrawl, Enter the Abyss, Mage Arena I/II, Barbarian Training, The Final Dawn, The Blood Moon Rises, …). The spec's name-mapping is not specified at all. *Resolution:* spec a three-step resolver in kb-build: (a) a committed `aliases.json` for the 10 RFD names, (b) fallback to the `|requirements=` field of `{{Quest details}}` wikitext (already fetched for items; `sote.txt` line 32 shows the `{{SCP|Skill|N}}` form), (c) miniquests get an entry with empty reqs. B2 then applies to the merged result; drop the `Name_of_quest` stub.

2. **BLOCKER — D1 has no formula and quests/diaries have no priority.** The ticket says the exact formula lives in one function with tests, yet the spec never defines `closeness`, and only milestones (B4) carry a `priority`, so `priority × closeness` is undefined for quests and diaries. Tests cannot be written first. *Resolution:* pin in the spec: `score = priority × closeness`, `closeness = 1 / (1 + unmet + xpDelta / 250_000)`; tie-break priority desc, then name asc; default priority per category (quest 5, diary tier 4, milestone/boss/slayer from JSON) overridable by a hand-curated `priorities.json`. State that `Item.have = unknown` gaps count as 0 unmet and the goal is labelled "bank unknown", never "Ready now".

3. **BLOCKER — C6 route simulation is under-specified; two implementers would diverge.** Open points: (a) exhaust materials vs switch when a higher method unlocks (the ticket example stops prayer potions at 66 with ranarr left, so switching is intended); (b) XP/action ties; (c) whether method outputs feed the simulated bank (needed for grimy→clean→potion chains); (d) `Module:Skill calc/Herblore` has only types Cleaning/Regular/Divine/Swamp tars/Barbarian — **no unfinished-potion method exists**, so the C7 "craft source points back at a B6 method" chain for `Toadflax potion (unf)` has nothing to point at. *Resolution:* spec the loop: at each step pick the highest-XP method with `level ≤ simLevel` (ties: lower level req, then name), take `min(affordable, ceil((xpAtNextUnlock − xp)/xpPerAction))` actions, mutate the simulated bank with materials consumed and outputs produced, repeat; exclude the Barbarian type (dose-variant inputs); import 0-XP intermediate recipes (unf potions) from Bucket `recipe` into methods.json so craft recursion has a target.

4. **IMPORTANT — Diary "goal" identity contradicts itself.** C1 and E1 make each diary *task* a goal; the ticket example and D4 ("not three diaries") treat the *tier* as the goal with tasks as the gap. *Resolution:* rule that the diary tier is the goal; unmet tasks are `DiaryTask` gap nodes carrying their own skill/quest/item reqs; tasks appear in the Focus picker as shortcuts to their tier.

5. **IMPORTANT — D4 "span two categories" is unspecified.** Neither the category set nor the selection algorithm nor interaction with pins is defined. *Resolution:* categories = `quest | diary | milestone | slayer_target | boss`; pins fill slots first; if the first two slots share a category, the third is the highest-ranked goal of a different category, else the third overall; if fewer than two categories have open goals, plain top three.

6. **IMPORTANT — "Persist on bank close" has no defined signal, and ruling 9's premise is wrong.** `ItemContainerChanged(BANK, 95)` fires on open and on each deposit/withdraw, not on close. The research has no close signal; verified on master: `net.runelite.api.events.WidgetClosed(groupId, modalMode, unload)` and `InterfaceID.BANKMAIN = 12`. *Resolution:* keep the latest BANK container copy from `ItemContainerChanged`; on `WidgetClosed` with `groupId == BANKMAIN` persist it, stamp "bank as of", and request a snapshot. Reword A4 to "snapshot within one tick of close; panel within the F5 budget".

7. **IMPORTANT — Threading hand-off has gaps beyond the client-thread rule.** (a) Panel clicks (Do this / Not now / Refresh) and `ConfigChanged` arrive on the EDT; the spec must say they re-run the engine on the executor against the *cached* snapshot, and only Refresh calls `clientThread.invoke`. (b) Store file I/O must run on the executor, not the client thread or EDT. (c) Quest state via `runScript` on `GameStateChanged(LOGGED_IN)` may read pre-sync varps; take the first snapshot on the first `GameTick` after login and verify in the dev client. (d) "Latest request wins" needs a generation counter so a stale engine result is discarded,.

8. **IMPORTANT — Diary bit mapping is verified for one tier only.** `VarrockEasy.java` bits 1–14 on `VarPlayerID.VARROCK_ACHIEVEMENT_DIARY (1176)` match wiki ordinals 1–14 exactly (bit 0 unused, so the rule is "bit N, 1-based"). Medium/Hard/Elite and the `_DIARY2` overflow are untested, and the spec puts A6 in S1 while the mapping ships in `diaries.json` (S2). *Resolution:* move A6 to S2; the plan must transcribe all 44 tier classes from Quest Helper and add a dev-client check per tier: popcount of the KB bit set equals the completed count in the in-game diary tab.

9. **IMPORTANT — Slice table leaves ACs uncovered and B1 contradicts B8.** F4 (Refresh + auto-refresh triggers), F5 (perf budgets), and G2 (no network) map to no slice; C9 says "(part)" without naming the remainder. B1 requires byte-identical output on rerun, but `generatedAt` (B8) changes every run. *Resolution:* F4 → S3, F5 → S5 with a timed JUnit case on a maxed fixture, G2 → S1 as a dependency-scan gate; derive `generatedAt` from the max fetched wiki revision timestamp so it is both meaningful and reproducible.

10. **IMPORTANT — Ironman-only requirements are not modelled.** Questreq carries `{'Prayer', 31, 'ironman'}` (Animal Magnetism) and diary pages carry ironman-only variants (Varrock Medium: Magic 49 for irons). Ticket decision 4 makes irons a first-class user; C4 filters sources only. *Resolution:* add `ironmanOnly: boolean` to skill reqs in quests.json/diaries.json and apply it in `GapEngine` for account types 1–6; treat GE exclusion the same for types 1–6 (group irons have no GE).

11. **SUGGESTION — Trigger filtering.** `VarbitChanged` and inventory `ItemContainerChanged` fire constantly; rather than rescanning 211 quest scripts on every debounced tick, trigger on `StatChanged` where level changed, `VarbitChanged` where `varbitId == QUEST_POINTS (101)` or `varpId ∈ 1176–1199`, bank close, login tick, and Refresh.

12. **SUGGESTION — Pin one RuneLite version.** The template uses `latest.release` for `client`; the spec pins `runelite-api:1.12.38` for engine tests. A drift produces a `Quest` enum that passes the KB test but differs at runtime. Use one `runeLiteVersion` for both.

13. **SUGGESTION — Schema holes.** Diary tasks have non-skill reqs ("50 kudos", "Jagex Account"); add `notes[]` (displayed, not evaluated) so the gap engine does not mark them met. Calc `type` can be `"Regular potions, Popular"`; split on comma. Note in the spec that B1's `scripts/build-kb` / `kb/*.json` paths become `kb-build/` and `plugin/src/main/resources/kb/`, and that milestones.json is hand-curated (ticket B1 vs B4 disagree).

No finding is marked NEEDS-HUMAN: every fork above has one clearly better option and is cheap to swap.
